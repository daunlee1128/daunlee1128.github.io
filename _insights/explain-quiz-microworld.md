에이전트가 만든 변경을 승인하면서 정작 그 코드가 어떻게 도는지는 설명하지 못했다. 그런 일이 반복됐다. 읽는 시간을 늘리는 대신 **설명·퀴즈·마이크로월드** 세 자리를 각각 도구로 채웠다. 지금은 그 셋이 기본 절차다. 아래는 각 자리에 어떤 도구와 어떤 프롬프트를 넣었는지, 그리고 어디서 안 통했는지다.

> 출발점은 AI Engineer World's Fair 2026 강연이다.
> Notion의 Geoffrey Litt, [Understanding is the New Bottleneck](https://www.youtube.com/watch?v=WkBPX-oDMnA).

원 강연의 기법은 설명(explain diff)·마이크로월드·공유 공간 셋이다. 내가 굴린 건 그중 둘에 퀴즈를 끼워 넣은 조합이다.

{: #why-not-reading}
## 정독을 그만둔 이유

코드가 아니라 내 머릿속에 빚이 쌓인다. 강연은 이걸 인지 부채(cognitive debt)라고 부른다.

| | 기술 부채 | 인지 부채 |
|---|---|---|
| 어디에 쌓이나 | 코드베이스 | 내 머릿속 |
| 왜 쌓이나 | 급해서 타협한 설계 | 구조를 모른 채 승인한 변경 |
| 언제 티가 나나 | 고치려 할 때 | 다음 아이디어를 내려 할 때 |
| 갚는 방법 | 리팩터링 | 구조를 다시 세우는 학습 |

기술 부채는 다음 사람이 같이 갚지만 인지 부채는 나 혼자 진다. 방치하면 "내 프로젝트인데 손을 못 대겠다"는 상태가 된다.

그렇다고 정독이 답도 아니다. 강연은 에이전트가 5만 줄짜리 PR을 날리는 상황을 전제로, 읽어라도 읽지 마라도 아닌 **읽는 방식을 바꿔라**를 결론으로 낸다.

| ① 설명 | `explain-diff-html` 스킬 | 변경 diff | 구조 먼저·코드 마지막 순서의 HTML 설명서 |
| ② 퀴즈 | NotebookLM, `explain-diff-html` | 위에서 만든 설명서 | 객관식·주관식 문항 |
| ③ 마이크로월드 | 로컬 Docker 스택 | 도구 자체 | 내 손으로 만져지는 실행 환경 |

스킬이라고 해도 결국 프롬프트와 출력 형식을 묶어 둔 것이다.

- `explain-diff-html` — 강연자가 공개한 스킬. 변경 diff를 구조 먼저·코드 마지막 순서로 설명하고 끝에 퀴즈를 붙인다
- `aws-diagram` — 내가 만든 스킬. 코드와 설계 문서를 읽어 아키텍처 다이어그램 HTML을 그린다

스킬을 만들지 않아도 된다. 아래 프롬프트를 그대로 붙여 넣으면 결과는 같다.

## ① 설명 — 구조부터, 코드는 맨 마지막

위에서 아래로 읽다가 지쳐 구조 파악을 포기한 적이 많다. 읽는 순서를 뒤집는 게 전부다.

```text
방금 바뀐 거 설명해줘. 나는 이 코드가 처음이니까
구조부터 이해시켜 주고, 코드는 맨 마지막에 보여줘.
```

이 한 줄이 산출물의 순서를 바꾼다. ① 이 변경이 시스템 어디에 붙는지 ② 흐름 한 줄 요약 ③ 그다음에야 실제 코드.

`explain-diff-html`은 강연자가 공개한 스킬이다. 설명서를 쓰고 끝에 퀴즈까지 같이 뽑는다.

```text
① 프로젝트 전체 구조를 먼저 설명하고 세부 내용은 맨 마지막에 보여줘.
   논리가 어떻게 연결되는지 파악하게 해줘.
② 핵심 구조를 제대로 이해했는지 스스로 테스트하고 싶어. 객관식·주관식 퀴즈를 내줘.
```

`aws-diagram`은 글로 흩어진 구조를 그림 한 장으로 바꾼다. "이 서비스의 인증 흐름을 시퀀스·인가 플로우 다이어그램으로 그려줘" 식으로 쓴다.

## ② 퀴즈 — 이해 속도를 재는 자리

읽는 것과 답하는 것은 다르다. Litt는 동료가 던진 기본적인 질문에 말문이 막힌 뒤로 규칙을 하나 세웠다. 퀴즈를 못 풀면 팀에 코드 리뷰를 보내지 않는다.

나도 비슷한 구멍이 있다. 거의 모든 업무를 Claude로 처리하지만 다음 셋 중 어느 것도 자신 있게 설명하지 못한다.

- 도구 권한을 어디까지 열어 뒀는지
- 컨텍스트가 어느 시점에 잘리고 무엇이 남는지
- 사내 자료가 어느 경로로 나가는지

매일 써도 이해가 따라오지는 않는다. 그래서 퀴즈는 점수를 매기는 장치가 아니라 **내가 무엇을 모르는지 찾아내는 장치**로 쓴다.

학습할 문서를 NotebookLM에 넣고 문항을 뽑아 직접 푼다. 세 문항 중 하나라도 근거를 대지 못하면 설명서로 되돌아간다.

{: #microworld}
## ③ 마이크로월드 — 띄워놓고 만진다

문서로만 읽으면 감이 안 오는 게 있다. Litt는 마이그레이션 스크립트가 이해되지 않자 "내가 직접 포팅하는 게임을 만들어줘"라고 시켜 버튼을 누를 때마다 파일이 옮겨가는 화면을 만들었다.

내 경우는 새 도구를 익힐 때다. Langfuse 관측 스택을 로컬에 Docker로 통째로 올리고 실제 트레이스를 흘려보낸다.

| 문서만 읽을 때 | 띄워놓고 만질 때 |
|---|---|
| 트레이스 구조를 글로 이해 | 스팬이 실제로 어떻게 중첩되는지 화면에서 확인 |
| 평가 기능이 있다는 것만 인지 | 유용성·환각·간결성 평가를 직접 돌려 결과를 봄 |
| 설정 항목 목록을 훑음 | 잘못 넣어서 깨뜨려 보고 무엇이 필수인지 파악 |

*출시할 코드를 만드는 게 아니라 나를 이해시키는 코드를 만드는 것 — 목적이 다르면 품질 기준도 다르다.*

## 구조를 아는 만큼 프롬프트가 달라진다

이 셋을 왜 굴리는지는 성능 이슈에 어떻게 반응하는지를 보면 드러난다. 식당으로 바꿔 보면 홀은 UI, 주방은 백엔드, 서빙 시간은 API다. "음식이 늦게 나와요"는 "이 화면 느려요"와 같은 말이다.

| 구조를 아는 정도 | 나오는 요청 | 무엇을 놓치나 |
|---|---|---|
| 모른다 | "성능 개선해줘" | 병목 위치를 지목하지 못한다 |
| 조금 안다 | "스케일아웃하자" | 화구가 하나면 홀 인원을 늘려도 주문표만 쌓인다. DB 한 대에 서버만 늘리는 것과 같다 |
| 더 안다 | "먼저 어디서 밀리는지 재고, 캐싱·쿼리 튜닝으로 원인을 줄이고, 그래도 남으면 앞에서 막자" | — |

만석인데 계속 손님을 받으면 이미 앉은 손님 음식까지 늦어진다. 그래서 대기표를 끊는다. 큐잉과 레이트 리밋이 같은 판단이다.

세 번째 요청은 세 번째만큼 이해한 사람만 쓸 수 있다. 구조를 아는 만큼 지금 상황에 맞는 선택지를 골라낼 수 있고 프롬프트의 질도 거기서 갈린다.

## 아쉬운 것

| 아쉬운 것 | 회피책 |
|---|---|
| 퀴즈를 AI가 낸다 — AI가 짚지 못한 구멍은 문항에도 없다 | 내가 막혔던 지점을 프롬프트에 직접 적어 문항을 요청 |
| 마이크로월드는 만드는 비용이 든다 | 한 번 쓰고 버릴 것에는 만들지 않는다. 두 번 이상 막힌 개념에만 |
| 상호작용을 넣을수록 산만해진다 | 조작 대상을 하나로 제한. 강연도 같은 경고를 한다 |
| 공유 공간 자리가 비어 있다 | 원 강연의 세 번째 기법인데 아직 팀 단위로 굴려보지 못했다. 지금 산출물은 전부 내 로컬에 있다 |

설명서를 만들어도 안 읽으면 그만이다. 도구가 이해를 대신해 주지는 않는다.

## 오늘 5분으로 해볼 것

최근 PR이나 작업 하나를 골라 이렇게 시켜 본다.

```text
방금 바뀐 거 구조부터 설명해주고 코드는 맨 마지막에 보여줘.
다 설명한 다음, 내가 이해했는지 확인할 퀴즈를 3개 내줘.
```

퀴즈 세 개 중 하나에서 막히면 그 자리가 인지 부채다. 세 개를 다 풀면 승인해도 된다.

세 도구가 모두에게 맞지는 않을 것이다. 각자에게 맞는 가장 빠른 이해 방법을 AI로 찾아내는 게 요점이다. 지금은 그걸 찾기에 나쁘지 않은 때다.
